## 七、备份与升级

### 7.1 备份

| 对象 | 方式 |
|------|------|
| 数据库 | 后台「系统设置 → 数据备份」（F3，推荐）；或 `mysqldump --single-transaction cccms > cccms_$(date +%F).sql` |
| 附件 | 打包 `server/public/storage/`（或依赖云存储自身的多副本 / 版本控制） |
| 配置 | `server/plugin/cccms/config/*.php`、环境变量 |
| 代码 | Git 仓库 |

**数据库备份（F3）要点**：

- 归档落 `server/runtime/backups/*.sql.gz`（**不在 `public/`**，整库快照含所有租户数据，禁止外链）；
  元信息在 `sys_db_backup`（sha256 / 引擎 / 表数 / 耗时 / 失败原因）。
- 引擎：优先 `mysqldump`（`--single-transaction --quick`，不锁表）；没装时自动降级 PDO 逐表导出，
  列表里 `pdo` 是黄标 —— **它没有跨表一致快照**，写入高峰的备份可能自相矛盾。
  自定义二进制路径：环境变量 `MYSQLDUMP_BIN`（默认 `mysqldump`）。
- 定时备份：内置任务「数据库定时备份」（`DbBackupTask`，默认**停用**，每天 02:30）在
  「定时任务」页启用；保留策略取 `backup.keep_count`（定时备份留几份）/ `backup.keep_days`（按天清理）。
- 还原：后台选表 + **手输库名**确认；系统会先自动做一份 `pre_restore` 备份，再执行还原。
  MySQL 的 DDL 无法回滚，**请安排在维护窗口**，并确认这段时间的写入可以丢。
- 能力边界：视图 / 触发器 / 存储过程 / 事件不备份；不做 binlog 增量 / PITR。

### 7.2 升级

**框架代码同步**：如果本项目衍生自上游 CCCMS 仓库，先拉取框架更新（见 [§1.10](01-CLI命令.md#110-cccmsupdate--从上游仓库同步框架更新) 或后台
「系统设置 → 自动升级」），再执行下面的例行命令：

```bash
cd server
composer install
php webman cccms:db-upgrade
php webman cccms:menu-sync
php webman cccms:perm-scan
php start.php reload

cd ../frontend && npm install && npm run build
```

> 升级前先备份数据库；`db-upgrade` 可安全重复执行（只会建缺失的表，**不会改已有表结构**）。
> `cccms:update` 升级完会自动跑一遍 `menu-sync` + `perm-scan` + 清缓存（与用户下拉「系统同步」同一实现）。

## 八、安全加固清单

| # | 项 | 说明 |
|---|----|------|
| 1 | 替换 `JWT_SECRET` | HS256 要求 >= 32 字节，随机生成 |
| 2 | 替换 `DATA_ENCRYPT_KEY` | 改动后历史加密字段无法解密，**不做密钥轮换** |
| 3 | 关闭 debug | 不要设置 `APP_DEBUG=true`（**默认即关闭**，由环境变量控制） |
| 4 | 数据库最小权限 | 不要用 `root` |
| 5 | `public/storage` 禁 PHP 解析 | 或切独立域名 / 云存储 |
| 6 | 开启登录验证码 | `security.login_captcha = 1` |
| 7 | 调整失败锁定阈值 | `security.login_fail_limit` / `security.login_fail_window` |
| 8 | 提高密码长度下限 | `security.password_min_length` |
| 9 | 缩短令牌有效期 | `security.token_ttl`（默认已为 2 小时；调大即扩大 XSS 有效窗口，体验由滑动续期兜住） |
| 10 | 删除 / 改密默认账号 | `admin / admin123` 上线即改 |
| 11 | Nginx 层限流 | 对 `/auth/login` 做 IP 维度限流 |
| 12 | 开启 HTTPS | 前端与后端统一经 HTTPS |
| 13 | 运行时目录权限 | `runtime/`、`public/storage/` 可写，其余只读 |
| 14 | 配置可信代理 | 反代部署必配 `security.trusted_proxies`，否则 IP 维度限流与审计日志失真，见 [02-安装部署 §4.4](../02-安装部署.md#44-反向代理下的真实-ip-溯源必配) |
| 15 | 收紧可观测端点 | `security.metrics_allow_ips` 只填抓取端地址（默认仅本机），见 [§十一](#十一可观测端点healthz-与-metrics) |
| 16 | 审计链巡检 | 把 `php webman cccms:log-verify` 接进每日巡检，非 0 退出即告警（见 [§1.12](01-CLI命令.md#112-cccmslog-verify--校验审计日志链定位篡改--删除)） |
| 17 | 检查命令接入 CI | 把 `data-scope-check` / `data-rule-check` / `write-guard-check` 接入 CI |

## 十一、可观测端点（`/healthz` 与 `/metrics`）

两个端点都是 `#[NoLogin]`，**靠 IP 白名单收敛**（`security.metrics_allow_ips`，
默认 `127.0.0.1,::1`）；非白名单来源一律返回 **404**（不是 403 —— 403 等于承认「这个路径存在」）。
探活 / 抓取请求**不写操作日志**（`OperationLog` 的 `SKIP_PATHS`）：它们是周期性机器请求，
写进 `sys_log` 既会淹没业务日志，也会让 `/metrics` 的请求量自反馈虚高。

| 端点 | 定位 | 返回 |
|------|------|------|
| `GET /ping` | **存活探针**：只证明进程能收请求，不碰任何外部依赖 | 200 `pong` |
| `GET /healthz` | **就绪探针**：MySQL / Redis / 磁盘 / 内存逐项检查 | 正常 200 + JSON 明细；任一失败 **503** 并指明失败项 |
| `GET /metrics` | Prometheus 抓取（`text/plain; version=0.0.4`） | 见下表指标 |

```bash
curl -s http://127.0.0.1:8787/healthz | jq
curl -s http://127.0.0.1:8787/metrics
```

### 11.1 指标一览

| 指标 | 类型 | 来源 |
|------|------|------|
| `cccms_up{component="mysql"\|"redis"}` | gauge | 与 `/healthz` 同一套探测 |
| `cccms_http_requests_total{window}` | gauge | `sys_log` 滚动窗口（默认 300s） |
| `cccms_http_errors_total{window}` | gauge | 同上，`status_code >= 400` |
| `cccms_http_request_duration_seconds{quantile}` | gauge | 同上，P50 / P95 / P99（取自 `cost`） |
| `cccms_http_path_requests_total{path,window}` | gauge | 同上，按路径归一化后聚合，**Top 20**（`Metrics::PATH_LIMIT`） |
| `cccms_http_path_errors_total{path,window}` | gauge | 同上，`status_code >= 400` |
| `cccms_http_path_duration_seconds{path,quantile="0.95"}` | gauge | 同上，只导出 P95（每路径只给一个分位，控条数） |
| `cccms_online_sessions` | gauge | Redis 会话索引（`OnlineSession::count()`） |
| `cccms_crontab_last_run_status{crontab_id,name}` | gauge | `sys_crontab_log` 最新一条（1 成功 / 0 失败 / 2 跳过 / 3 超时） |
| `cccms_crontab_last_run_timestamp_seconds` | gauge | 同上 |
| `cccms_disk_free_bytes` / `cccms_disk_total_bytes` | gauge | 运行时目录所在分区 |
| `cccms_memory_usage_bytes` / `cccms_memory_limit_bytes` | gauge | `memory_get_usage(true)` / `php.ini memory_limit`（0 = 未限制） |
| `cccms_metrics_scrape_timestamp_seconds` | gauge | 本次抓取时间 |

服务器资源（F6，来源 `/proc`、`Redis::info()`、`SHOW GLOBAL STATUS`；非 Linux 环境只输出 `# HELP` / `# TYPE`
声明、不产生样本行 —— 冒号前的指标名仍在，抓取端照常解析，只是查不到数据）：

| 指标 | 类型 | 来源 |
|------|------|------|
| `cccms_node_cpu_seconds_total{mode}` | counter | `/proc/stat` 各模式累计秒数，占用率由抓取端 `rate()` 求值 |
| `cccms_node_cpu_count` | gauge | `/proc/cpuinfo` 的 `processor` 行数 |
| `cccms_node_load{period="1"\|"5"\|"15"}` | gauge | `sys_getloadavg()` |
| `cccms_node_memory_total_bytes` / `_available_bytes` | gauge | `/proc/meminfo`（`MemTotal` / `MemAvailable`） |
| `cccms_node_memory_used_percent` | gauge | `(MemTotal - MemAvailable) / MemTotal` |
| `cccms_node_processes` | gauge | `/proc` 下纯数字目录计数 |
| `cccms_node_uptime_seconds` | gauge | `/proc/uptime` |
| `cccms_redis_used_memory_bytes` / `cccms_redis_connected_clients` / `cccms_redis_ops_per_second` | gauge | `Redis::info()` |
| `cccms_redis_rejected_connections_total` | counter | 同上（`maxclients` 拒绝数） |
| `cccms_mysql_threads_connected` / `cccms_mysql_threads_running` | gauge | `SHOW GLOBAL STATUS` |
| `cccms_mysql_connection_usage_percent` | gauge | `Threads_connected / max_connections` |
| `cccms_mysql_questions_total` / `cccms_mysql_slow_queries_total` | counter | 同上 |
| `cccms_mysql_uptime_seconds` | gauge | 同上 |

> 看板（`GET /monitor/server`）与上述指标同源（`support/ServerMetrics.php`），区别只在于看板会
> **现场隔 200ms 采两次 `/proc/stat`** 直接算出 CPU 百分比 —— 这一步不放进 `/metrics`，否则每次抓取都要阻塞 200ms。

> **为什么不用进程内计数器**：Webman 是多进程常驻模型，进程内计数只反映「当前 worker 处理过多少」，
> 多实例部署下完全失真。这里统一从**可共享来源**（`sys_log` / Redis / 数据库）派生，
> 换来跨进程、跨实例口径一致。代价是指标精度受日志保留策略影响。
>
> 磁盘 / 内存阈值（探针用）写在 `support/HealthProbe.php` 顶部常量：磁盘剩余 < 5%、
> 进程内存占用 >= `memory_limit` 的 90% 判为不健康；`memory_limit = -1` 时只报用量不判故障；
> 容器文件系统拿不到容量信息时只标记 `unsupported`，**不误报故障**。

### 11.2 接入 Prometheus

```yaml
scrape_configs:
  - job_name: cccms
    metrics_path: /metrics
    static_configs:
      - targets: ['10.0.0.5:8787']
```

把抓取端地址（或网段，如 `172.18.0.0/16`）填进后台「配置管理 → 安全 → 可观测端点白名单」，
否则抓取会拿到 404。本机回环地址（`127.0.0.1` / `::1`）默认在白名单里，无需额外配置。

**告警规则**（阈值与后台「配置管理 → 监控」的 `monitor.*` 默认值一致，改一处要同步改另一处，
否则会出现「看板红了但告警没响」）：

```yaml
groups:
  - name: cccms
    rules:
      # CPU 占用率 = 1 - (idle + iowait) / 全部；与看板口径一致（iowait 不算忙）
      - alert: CccmsCpuHigh
        expr: |
          (1 - sum(rate(cccms_node_cpu_seconds_total{mode=~"idle|iowait"}[5m]))
             / sum(rate(cccms_node_cpu_seconds_total[5m]))) * 100 > 85
        for: 10m
        labels: { severity: warning }
        annotations:
          summary: 'CPU 使用率超过 monitor.cpu_threshold（默认 85%）'

      - alert: CccmsMemoryHigh
        expr: cccms_node_memory_used_percent > 90
        for: 10m
        labels: { severity: warning }
        annotations:
          summary: '系统内存使用率超过 monitor.memory_threshold（默认 90%）'

      - alert: CccmsDiskHigh
        expr: (1 - cccms_disk_free_bytes / cccms_disk_total_bytes) * 100 > 90
        for: 30m
        labels: { severity: critical }
        annotations:
          summary: '运行时目录所在分区已用超过 monitor.disk_threshold（默认 90%）'

      - alert: CccmsMysqlConnectionsHigh
        expr: cccms_mysql_connection_usage_percent > 80
        for: 5m
        labels: { severity: warning }
        annotations:
          summary: 'MySQL 连接数占 max_connections 超过 monitor.connections_threshold（默认 80%）'

      - alert: CccmsComponentDown
        expr: cccms_up{component=~"mysql|redis"} < 1
        for: 2m
        labels: { severity: critical }
        annotations:
          summary: '依赖组件不可用（{{ $labels.component }}）'

      # 被 maxclients 拒绝是「已经连不上了」，不是趋势问题：一出现就告警
      - alert: CccmsRedisRejectedConnections
        expr: increase(cccms_redis_rejected_connections_total[5m]) > 0
        for: 1m
        labels: { severity: critical }
        annotations:
          summary: 'Redis 因 maxclients 拒绝连接'
```

> 非 Linux（开发机的 Windows / macOS）不导出 `cccms_node_*`，上述规则在这些环境会「无数据」而不是误报。

## 十二、CI 与质量门禁

### 12.1 后端（`.github/workflows/php.yml`）

触发条件：`server/**` 或该工作流本身变更时（push / PR 到 `main`）。

| 步骤 | 内容 |
|------|------|
| 环境 | PHP 8.3 + 扩展 `pdo` / `pdo_mysql` / `pcntl` / `redis` / `mbstring` |
| 服务 | `mysql:8.0` + `redis:7-alpine`（带健康检查）；并设 `CCCMS_TEST_REQUIRE_SERVICES=1`，**集成用例跳过即失败** |
| 依赖 | 缓存 `server/vendor`；`composer validate --no-check-publish` + `composer install` |
| 供应链 | `composer audit --no-dev`（生产依赖有中高危漏洞即失败） |
| 静态分析 | `composer analyse`（PHPStan level 5 + baseline） |
| 基线门禁 | `phpstan-baseline.neon` 条目数 > 32 即失败（只许减不许增，防止用「追加基线」绕过检查） |
| 代码风格 | `composer cs:check`（php-cs-fixer `@PSR12`，只查 `plugin/` 与 `tests/`） |
| 初始化 | 导入 `db/schema.sql` 与 `db/seed.sql` |
| 同步 | `cccms:menu-sync` + `cccms:perm-scan` |
| 门禁 | `cccms:perm-scan --check` → `cccms:data-scope-check` → `cccms:data-rule-check` → `cccms:write-guard-check` → `cccms:openapi-check` |
| 测试 | `composer test` |

> `composer validate` **故意不加 `--strict`**：`composer.json` 仍保留空 PSR-4 前缀
> （`"": "./"`，插件自动加载依赖它），会被 `--strict` 判为警告而非错误。

### 12.2 前端（`.github/workflows/frontend.yml`）

触发条件：`frontend/**` 或该工作流本身变更时。

| 步骤 | 内容 |
|------|------|
| 环境 | Node 20 + npm 缓存（`frontend/package-lock.json`） |
| 依赖 | `npm ci` |
| 供应链 | `npm audit --omit=dev --audit-level=high`（**只审生产依赖**，见下） |
| 门禁 | `npm run format:check` → `npm run lint` → `npm run i18n:check` → `npm run test:coverage` → `npm run build`（含 `vue-tsc --noEmit`） |

> `npm run i18n:check`（`scripts/check-i18n.mjs`）用 esbuild 编译语言包后比对 `zh-CN` / `en-US`
> 的命名空间与 key 集合，**不一致直接失败**；另会列出仍有硬编码中文的非注释行，仅提示不影响结果。
>
> 审计门禁**刻意加 `--omit=dev`**：只覆盖随产物上线的生产依赖。开发依赖里的告警
> （`vite` / `esbuild` 的**开发服务器**问题）不进生产包，而修复它们需要跨多个大版本
> （Vite 5 → 8），风险与收益不匹配；该取舍登记在 [开发计划](../开发计划.md) 的 R-03 条目下。

### 12.4 检查命令的能力边界（X-14）

其中四个是**静态字符串 / 正则扫描**（不解析 AST、不执行代码），因此「检得出」的是
**固定写法**，绕开固定写法就检不出；`cccms:openapi-check` 例外，它走**运行时反射**
（真实路由表 + 控制器方法体），不受字符串写法影响。别把「通过检查」当成「绝对安全」——
它们收敛的是最常见的错误，边界之外靠代码评审兜底。

| 命令 | 检得出 | 检不出（绕开固定写法就漏） |
|------|--------|------------------------------|
| `cccms:perm-scan --check` | slug 格式非法 / slug 全局重复 / `Restrict` 方法非法 / 控制器公开方法缺注解（fail-closed） | **缺路由**：注解只扫控制器，不知道 `route.php` 里有没有对应的 `Route::xxx()`（`disableDefaultRoute` 下缺路由 = 接口**不存在**，扫描不报）—— 这一类由下面的 `openapi-check` 覆盖 |
| `cccms:openapi-check` | 路由指向不存在的方法 / 有注解但无路由可达（死接口）/ 非 NoLogin 缺鉴权属性 / slug 格式或唯一性 / 文档分组与接口数统计 | **参数覆盖度**：参数靠方法体里的 `$request->get('x')` 静态推断，写成 `$params = $request->get(); $x = $params['y']` 会漏；**闭包路由**（无控制器可反射）不纳入文档；**约定外的鉴权**（自定义中间件判权）不体现在注解上 |
| `cccms:data-scope-check` | R1 控制器直连库（`Db::name(` / `Db::table(` / `Db::query(`）；R2 受控表缺模型 / `$dataScope=false` / Logic 层用 `Db::name('受控表')` | 字符串匹配的变体：`$db = 'Db'; $db::name(...)`、`Db::{$method}(...)`、通过**别的方法/类间接**直连（`SomeHelper::query()` 内部 `Db::query`）、拼出来的表名（`Db::name($var)`） |
| `cccms:data-rule-check` | 规则声明里的静态冲突（区间无交集、动作互斥等） | 运行时动态构造 / 从库表读出来再拼的规则 |
| `cccms:write-guard-check` | 数组形参出现在 `insert/insertGetId/insertAll/update/save/replace` 实参里，且方法体（或同类一跳委托）无 `FilterInput::only(` | 把形参**改名/加工后再写**（如 `$rows = $data; ->insert($rows)`）、**>1 跳**委托、动态方法名 `->{$m}($data)`、非数组形参但内部拼数组写库 |

**「缺路由」这一类已自动化**：`cccms:openapi-check` 直接读运行时路由表（含 `config/route/*.php`
的 `glob` 动态加载）再按 `[XxxController::class, '方法名']` 反查，等价于下面这段人工差集，
且不会因动态加载而误报：

```bash
# 人工兜底的等价思路（已由 cccms:openapi-check 覆盖，保留以备排查命令本身的行为）
cd server
grep -rPn "^\s*public function \w+" plugin/cccms/app/controller | sed -E 's/.*public function (\w+).*/\1/'
grep -oPn "Route::(get|post|put|delete)\('/[^']+'" plugin/cccms/config/route.php
```

> 注意：**不要**再用纯静态 grep 做这个差集 —— 路由声明允许 `glob` 动态加载业务插件的
> `config/route/*.php`，静态扫描会把动态部分全部误报成「死接口」。用 `openapi-check`，
> 它走的是框架真实加载后的路由表。
