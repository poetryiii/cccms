## 三、文档编写规范

新增或修改文档时，请遵守以下约定，保持整套文档**风格一致、可检索、可维护**。

### 3.1 文件与命名

- 文件名使用「**两位序号 + 中文标题**」：`NN-标题.md`，序号决定阅读顺序。
- 标题与文件名保持一致；新增章节插入时，**顺延后续序号**（宁可重排，也不要出现 `04-1`）。
- 一个文件只讲一件事；文件过长（超过约 800 行）时按主题拆分为目录 + 子文件。

### 3.2 结构

每份文档遵循统一骨架：

```markdown
# 标题

> 一句话导读（本文讲什么、适合谁看）

---

## 一、二级标题（用中文数字）
### 1.1 三级标题
```

- 一级标题只有文档标题一个；正文从 `## 一、…` 开始。
- 关键结论用 `> **提示**：` / `> ⚠️ **注意**：` 引用块强调。
- 涉及「为什么这样设计」时，单独用「设计说明」小节说明，不要混在步骤里。

### 3.3 写作约定

- **统一术语**：插件（plugin）、控制器（Controller）、逻辑层（Logic）、模型（Model）、权限节点（slug）、受控表、预设基线、`fail-closed`。首次出现时给出中英文对照，之后只用中文。
- **代码块必须标注语言**（```php / ```bash / ```sql / ```ts / ```vue）。
- **命令统一写在 `bash` 代码块**，路径以仓库根为基准。
- **表格优先**：枚举型内容（参数、常量、字段、接口）一律用表格。
- **不粘贴大段源码**：只贴「签名 + 关键几行」，并注明文件路径，让读者自己去翻代码。
- **交叉引用用相对链接**：`[数据权限](06-数据权限.md)`，并锚点到小节（如 `06-数据权限.md#三角色级预置范围`）。
- **不要写「将来会……」「计划……**」之外的内容**：未实现的能力要么写进 `../待办.md`，要么用 `> ⚠️ 本能力尚未实现` 明确标注。
- **文档要随代码一起改**：改动机制、接口、命令、配置时，必须同步更新对应文档；`../待办.md` 中已注明「文档同步」的事项视为完成标准的一部分。

### 3.4 图片与图表

- 优先使用 ASCII / Mermaid 绘制流程，避免二进制图片（便于 diff）。
- Mermaid 示例：

```mermaid
flowchart LR
  A[请求] --> B[CheckLogin]
  B --> C[CheckAuth]
  C --> D[Controller]
```

### 3.5 文档状态标记

对暂缺或过期的内容，用统一标记，避免读者误解：

| 标记 | 含义 |
|------|------|
| `> 待补充：…` | 已知缺口，欢迎补充 |
| `> 已废弃：…` | 历史机制，仅为兼容保留 |
| `> ⚠️ 陷阱：…` | 极易踩坑、必须注意 |
