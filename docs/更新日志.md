### 安全

- **移除 JWT 密钥的公开默认值兜底（P0-1）**：`config/auth.php` 不再回退到仓库内可见的默认密钥，
  `JWT_SECRET` 未配置或不足 32 字节时由新增的 `support/SecurityBootstrap.php` 在**启动期**直接失败，
  而不是静默用弱密钥签发令牌。同时修复根因：`composer.json` 缺少 `vlucas/phpdotenv`，
  导致 `.env` **从未被加载**、所有配置静默回落到硬编码默认值。
- **消除同域存储型 XSS（P0-2）**：上传白名单移除 `svg`；`StorageDriver` 新增危险扩展名硬拒绝名单
  （`svg` / `html` / `xml` / `mhtml` 等，**优先于后台白名单**）与魔数内容校验；
  新增静态文件中间件 `app/middleware/StorageGuard.php`，`/storage/` 下非图片 / PDF 强制
  `Content-Disposition: attachment` 并全局下发 `X-Content-Type-Options: nosniff`。
- **登录失败锁定增加 IP 维度（P1-1）**：`LoginThrottle` 由单一账号维度拆为
  `cccms:login_fail:user:{用户名}` 与 `cccms:login_fail:ip:{IP}` 双维度；IP 维度达阈值只限流该 IP、
  **不锁账号**，避免攻击者用错误密码锁死他人账号。新增配置 `security.login_fail_ip_limit`（默认 20）。
- **全站接口限流（P1-2）**：新增 `support/RateLimiter.php`（Redis 固定窗口计数）+ 中间件
  `app/middleware/RateLimit.php`，按「每用户每路由」限流，重接口（`export` / `import` / `generate`）
  单独更严的阈值，超限返回 `429` + `Retry-After` / `X-RateLimit-*` 响应头；
  Redis 不可用时 **fail-open**（不因缓存故障挡业务）。新增 4 项 `security.rate_limit_*` 配置。
- **强化密码策略（P1-4）**：`PasswordPolicy` 新增长度上限（默认 64，避免超长口令放大 bcrypt 开销）、
  内置弱口令黑名单（约 90 条，含中文环境常见口令）、字符类别数要求（默认 2 类）、
  「不得与用户名 / 昵称 / 邮箱相同或包含」；并**补齐了 `UserLogic::update` 此前完全缺失的策略校验**。
  新增配置 `security.password_max_length` / `security.password_strength`。
- **CORS 白名单可配置化（P1-6）**：新增 `config/cors.php`（`CORS_ORIGIN`，默认留空 = 仅同源）；
  `Cors` 中间件改为**命中白名单才下发整组 CORS 头**并原样回显 Origin（不返回 `*`），
  带 `Origin` 时无条件 `Vary: Origin`。
- **令牌生命周期改造：缩短 TTL + 滑动续期（P1-3）**：`security.token_ttl` 默认值由 **7 天缩短为 2 小时**
  （令牌存 localStorage，TTL 就是 XSS 一旦发生攻击者能用的窗口长度）；新增滑动续期 ——
  `CheckLogin` 在剩余有效期不足 TTL 的 1/3 时签发新令牌并经响应头 `X-Refresh-Token` 下发，
  前端 `api/request.ts` 静默替换，活跃用户不掉线。续期后 `OnlineSession::rotate()` 把在线会话
  迁到新 `jti`（否则「强制下线」踢的是已废弃的旧令牌）；旧令牌**不写入黑名单**，避免并发请求被判 401。
- **收敛字段级 `encrypt` 密钥的下发范围（P1-5）**：`crypto_key` 改为**只下发给持有
  `cccms:data_rule*` 权限节点的管理员与超管**（`AuthLogic::mayDecryptFields()`），
  普通账号 `/auth/me` 不再返回；文档明确写出「`encrypt` 是存储加密、**不是**访问控制」，
  规则配置页选择 `encrypt` 动作时展示风险提示。
- **反代场景下的真实 IP 溯源（R-01）**：原先各处直接用 Webman 的 `$request->getRealIp()`，
  它在「直连 IP 属内网」这一分支取 `X-Forwarded-For` 的**第一个**值 —— 而本系统正是
  Docker / Nginx 反代部署（直连 IP 必然是网关内网地址），因此攻击者只要每次伪造一个 XFF
  就能让 **IP 维度**的登录失败限流（`security.login_fail_ip_limit`）形同虚设，
  还能把假 IP 写进登录日志与操作日志。新增 `support/ClientIp.php`：
  **仅当直连来源命中 `security.trusted_proxies`（CIDR 白名单）时才解析转发头**，
  并采用「**取最右非可信 IP**」标准算法（从 XFF 最右端向左跳过所有可信代理，
  第一个非可信地址才是真实客户端），攻击者在左侧拼接的伪造条目永远先被自己的真实出口挡住；
  未配置白名单或直连来源不可信时一律回退直连 IP（安全默认）。
  6 处调用点（登录限流 / 登录日志 / 在线会话 / 操作日志 / 慢接口告警 / 找回密码 IP 限流）
  统一改走 `ClientIp::resolve()`；新增配置项 `security.trusted_proxies`（`db-upgrade` 幂等补插），
  部署要求与 Nginx 样例见 [02-安装部署 §5.4](02-安装部署.md#54-反向代理下的真实-ip-溯源必配)。
  新增用例 `ClientIpTest`（CIDR 匹配含 IPv6、XFF 解析丢垃圾条目与剥端口、
  未配置白名单 / 直连不可信 / 多级代理四类算法分支）。
- **写入口字段白名单（R-02，防 Mass Assignment）**：写接口把 `$request->post()` **整数组**
  交给 Logic，可写字段集合原本是**隐式**的（靠模型声明 + `ScopedQuery` 剔除
  `hidden` / `readonly` / `mask` / `encrypt`），新增字段时容易漏判。现在：
  `support/FilterInput.php` 新增 `only(array $raw, array $allow)`；13 个 Logic 的 22 个写方法
  显式声明白名单并在入口过滤（`$data = FilterInput::only($data, self::FIELDS)`）。
  已有 4 处各自实现的等价白名单（`CategoryLogic::pick` / `DataRuleLogic::prepare` /
  `CrontabLogic::prepare` / `NoticeLogic::prepare` / `TenantLogic::pick` / `ProfileLogic::update`
  的内联 `array_intersect_key`）统一改为调用它，全项目只留一份实现。
  新增静态校验 `support/WriteGuardChecker.php` + 命令 `cccms:write-guard-check`（已入 CI）：
  凡「数组形参被整行写库」（`insert` / `insertGetId` / `insertAll` / `update` / `save` / `replace`）
  的方法必须声明白名单，允许**一跳**委托（如 `self::prepare($data)`），
  逃生口为 `// @write-guard-ignore`（须写明理由）。代码生成器的 Logic 模板同步产出
  `FIELDS` 常量与过滤调用（按表结构排除主键与系统维护列），生成即合规。
  新增用例 `WriteGuardTest`（白名单语义 + 全量代码扫描 0 错误）。
- **本轮全量回归**（R-01/R-02/R-03/R-05/R-09/R-10/R-11/P1-7/P2-12/P2-14 落地后）：
  后端 `php tests/run.php` **112 通过 0 失败 0 跳过**（新增 `ClientIpTest` / `WriteGuardTest` /
  `ObservabilityTest` / `LogChainTest` / `LoginThrottleTest` / `TenantBoundaryTest` 六个用例文件）、
  `composer cs:check` 0 违规（247 个文件）、PHPStan level 5 + baseline 无报错、
  `cccms:perm-scan --check` / `data-scope-check` / `data-rule-check` / `write-guard-check` 全部通过、
  `cccms:db-upgrade` 重复执行为 **0 变更**（幂等）、`composer audit --no-dev` 无告警；
  前端 `npm run format:check` / `lint` / `i18n:check` / `test:coverage`（76 条）/
  `build` 全部通过。
- **审计日志防篡改：`sys_log` 链式哈希（P2-14）**：日志原先由应用直接 `INSERT`，
  任何拿到库权限的人都能 `UPDATE` 掉「我改过这条记录」或 `DELETE` 掉整段，而**事后无法区分**
  「本来就是这样」与「被人改过」——归档解决的是容量，不是可信。现在 `sys_log` 增加
  `prev_hash` / `row_hash` 两列（`sha256(prev_hash + 规范化的行内容)`），并新增单行表
  `sys_log_chain` 记录链尾（`tail_id` / `tail_hash`）与**校验起点**（`anchor_id` / `anchor_hash`）。
  - **唯一写入入口** `support/LogChain.php`：操作日志中间件与登录日志都改走它
    （登录日志原先用 `OperationLog::withoutGlobalScope()->insert()` 跳出数据权限，
    现在直连查询构造器，连模型层的作用域与字段规则都不经过，对审计写入更安全）。
    它用 `SELECT ... FOR UPDATE` 锁住链状态行，把「读链尾 → 插入 → 推进链尾」放在同一事务里
    —— 否则并发请求会读到同一个 `prev_hash` 写出**分叉链**，校验时凭空多出断点。
  - **链尾必须单独落一行**：只查 `MAX(id)` 无法发现「尾行被删」，而删尾正是最常见的掩盖手段。
  - `support/LogVerifier.php` + 命令 `cccms:log-verify`（`--from` / `--to`）按 id 顺序重算并比对，
    能区分 `content_modified`（改过内容，**直接报出该行 id**）、`link_broken`（中间行被删）、
    `tail_stale`（尾行被删 / 替换）、`chain_missing`（状态行被整行删掉）；退出码非 0 即发现断点，
    可直接接进巡检与告警。实测：改掉中间一行 → 定位到该 id 并退出 1；改回 → 恢复通过。
  - **刻意不报为问题**的情形：未入链的历史行（`row_hash` 为空，含本能力上线前的数据与
    降级写入）只统计不报错；校验起点那行的 `prev_hash` 不校验（前驱已被合法归档 / 清理）；
    链**中间**的合法删除（管理员删日志）与篡改在数据上不可区分，因此如实报出并交给人工判断。
  - **归档协同**：`LogArchiver` 每批额外上传 `<文件>.chain.json`（段边界哈希 + `unchained` 条数
    + 归档时实测的 `broken_at`），归档后调 `reanchor()` 前移校验起点；`LogCleanTask` 与
    `LogLogic::delete/clear` 同样 reanchor。发现链不自洽时数据仍归档（不能丢数据），但命令以退出码 `1` 结束。
    归档内容经过二次脱敏，**无法**用它重算行哈希 —— 行哈希的正确性由归档时的 `broken_at` 固化。
  - **失败态度 fail-open**：链表 / 列不存在（升级未执行）、库偶发不可用、锁等待超时，
    一律降级为「不带哈希的普通插入」并记 error 日志 —— 链式哈希是加固能力，
    丢日志比少一层校验更糟。降级写入的行 `row_hash` 为空，校验时按「未纳入链」处理。
  - 升级：`cccms:db-upgrade` 补两列 + 建 `sys_log_chain` 表（幂等）；新增用例 `LogChainTest`（6 条）
    覆盖规范化口径、写入后链自洽、三类断点的定位、以及「历史行不误报」。
  - ⚠️ 开发中踩到并已修正的坑（写进注释）：**必须先算哈希再挂 `prev_hash`** ——
    `normalize()` 只产出 16 个业务字段，若把 `prev_hash` 混进参与哈希的载荷，
    校验侧永远算不出同一个值，表现为「所有行都被判为已篡改」。

### 新增

- **自动升级新增「强制对齐上游」档（`--force-all`）**：下游落后太多、想整体对齐上游时，原来的
  三方比对会把「本地已改 / 本地已删除」当成定制而保留，永远追不上。现在 `cccms:update --force-all`
  把这些也覆盖 / 恢复、并删除「上游已移除」的文件（全部先备份）；后台「自动升级」页新增对应勾选
  （`force_all` 透传到 `/upgrade/run`）。命令行 / 页面 / `Upgrader::apply()` 三处同步支持。
- **导出异步化 / 导出任务中心（P2-7）**：日志导出原本**同步**返回文件流，响应时间随数据量线性增长，
  前端 axios 超时 15s，大表导出直接超时。现在 `GET /log/export` 先数行数：`<= 10000` 行仍同步返回
  CSV（小数据量体验不变），超过则只落一条 `sys_export_task`（新增表）就返回 `{async, task_id, total}`。
  - **消费**：内置定时任务 `ExportTaskConsumer`（默认每 10 秒）认领待处理任务，用「id 游标 + 每批 1000 行」
    的 keyset 分页**流式**写 CSV（`Csv::writeRow`，复用同一套公式注入防护），10 万行也内存恒定；
    归档落在 `runtime/exports/`（**不进 `public/storage`** —— 导出含敏感日志，绝不能放进无需鉴权的静态目录）。
  - **下载走归属校验**：`GET /export/task/list` + `GET /export/task/download`（都是 `#[NoAuth]` 登录即可，
    但按 `user_id` 归属过滤），越权下载表现为「不存在」；未完成提示稍后、文件被清理提示重新导出。
  - **过期清理**：`export.keep_minutes`（默认 60 分钟），消费者每次 tick 顺带清理过期文件并置「已过期」。
  - **认领防并发**：消费前先 `UPDATE ... WHERE status=pending` 抢占（命中 1 行才算认领成功），
    多个消费者不会重复生成同一份。
  - **前端（已升级为全局面板 + 全异步）**：导出任务中心从日志页抽屉上移为**顶栏右上角全局入口**
    （带未完成角标、有未完成任务才轮询），新建 `stores/exportTask.ts` + `components/ExportTaskDrawer.vue`；
    `GET /log/export` 改为**一律异步**（不再区分数据量），各模块的导出统一投递到该面板查看与下载，
    未来新增导出类型会自动出现在面板里。
  - 新增用例 `ExportTaskTest`（5 条，需库）：落任务 → 消费生成归档 → 归属校验 → 未完成拒绝 → 过期清理。
- **附件分片上传 / 秒传（P2-9）**：单请求上传受 `upload.max_size`（默认 10MB）限制、弱网失败要
  整包重传，大文件基本传不上。现在同一个「上传」按钮按体积自动分流：`> 10MB` 走
  `init → chunk → complete` 三阶段（前端 `el-upload` 改自定义 `http-request`，统一走 axios 实例）。
  - **三阶段**：`/file/upload/init`（校验类型 / 总大小 → 尝试**秒传** → 建 Redis 会话，
    权限节点 `cccms:file:upload:chunk`）→ `/file/upload/chunk`（逐片落盘 `runtime/chunks/{id}/`，
    幂等可重传，单片上限 8MB）→ `/file/upload/complete`（校验片齐 → 流式合并 → 校验大小 / 哈希 →
    交回 `FileLogic::upload` 入库）。后两步是 `#[NoAuth]`：没有独立可授权语义，会话只能由
    「通过了 init 校验的本人」创建，`ChunkUpload::load()` 再校验归属，无节点也不会被越权。
  - **秒传**：前端对 ≤ 64MB 的文件用 WebCrypto 算 SHA-1（与服务端 `sha1_file` 同口径），
    `init` 命中「内容 hash + size 相同且**在数据范围内可见**」时直接复用记录，连字节都不传；
    非 HTTPS 环境算不出哈希则跳过秒传（不影响续传）。哈希只在 init 当**快速路径键**用，
    入库的 hash 永远是服务端算的 —— 伪造哈希最多得到「没命中」。
  - **断点续传**：`init` 返回 `received` 已收分片列表，前端只补缺片。
  - **完整性**：合并后总字节数必须等于声明大小，声明了哈希的还要 `sha1_file` 对得上 ——
    挡住「漏传一片生成损坏附件」与「伪造秒传」。写进测试的 `content_modified`-式 bug：
    分片合并用流式 `stream_copy_to_stream`，不整文件读进内存（100MB 会撞 `memory_limit`）。
  - **四种驱动行为一致**：分片只暂存本地，`complete` 把合并文件当成普通上传交给驱动
    （本地 `rename`、云驱动整体上传）；云厂商原生分片接口本轮不做（四套 + 真账号联调，取舍见开发计划）。
  - **大小上限显式传参**：新增 `StorageDriver::upload($file, ?int $maxBytes)` 一路透传到
    `FileLogic::upload(..., $maxBytes)`，分片走 `upload.chunk_max_size`（默认 2048MB）。
    之所以不设成员/静态变量：驱动实例被 `StorageManager` **静态缓存**（多请求共用一个对象），
    可变状态会在并发请求间串味，出现「这次放行 2GB、下个请求也跟着放行」。
  - **清理**：会话 Redis TTL 24h；磁盘目录由内置任务 `ChunkCleanTask`（每小时，新装 seed 内置、
    存量库在任务页新增）与 `init` 顺带清理（每小时节流一次）按 mtime 回收；`complete` 无论成败都清。
  - 新增用例 `ChunkUploadTest`（9 条，需库 + Redis）：危险扩展名 init 即拒、秒传命中、
    完整流程端到端、大小不符 / 哈希不符拒绝、会话归属隔离、超时目录清理。
- **列表批量操作（P2-1）**：用户 / 岗位 / 字典三个模块支持批量启停与批量删除，用户额外支持
  **批量分配角色 / 部门 / 岗位**（整体替换语义：传了哪个键就重设哪个关联）。新增 9 个接口
  （`POST /user/batchStatus|batchDelete|batchAssign`、`/post/batchStatus|batchDelete`、
  `/dict/batchStatus|batchDelete|batchStatusData|batchDeleteData`）与 9 个权限节点。
  统一语义为「**只作用于可见行 + 跳过并回报 + 不整批失败**」：越权行、超管账号、操作者自己、
  下挂用户的岗位一律计入 `skipped` 并回传 `{affected, skipped[]}`，前端降级为 warning 并说明原因。
- **角色复制 / 权限模板（P2-2）**：新增 `POST /role/copy` + 节点 `cccms:role:copy`。复制角色本体

- **上传记录的 MIME 改存服务端探测值（R-07）**：附件入库的 `mime` 原先取
  `UploadFile::getUploadMimeType()`（**客户端上报值**，可任意伪造）。现在统一走
  `StorageDriver::probeMime()` 的 finfo 探测结果，客户端值仅在「探测不到」时兜底
  （finfo 不可用，或内容无魔数被识别为 `application/octet-stream`），避免整列退化成
  `octet-stream`。探测发生在**校验阶段**并随 `validate()` 一并返回 —— 本地驱动紧接着就把
  临时文件 `move()` 走，之后已无法探测；`assertContentMatches()` 复用同一份 finfo 探测，
  但**刻意不做回退**（回退会让魔数校验形同虚设）。新增用例 `StorageMimeTest`

### 性能

- **`SysConfig` 缓存防击穿（R-08）**：整表配置缓存在 key 过期 / Redis 冷启动的瞬间，
  并发请求会同时查库回填。现在回填前加一把 Redis `SET NX EX` 短锁
  （`cccms:config:lock`，TTL 5s，跨 phpredis / predis 行为一致，不引入 Lua）：
  只有抢到锁的请求查库并 `toCache()`，持锁期间结束即 `DEL` 释放；
  抢不到锁的请求等 20ms 后二次读缓存，仍拿不到就直读库兜底（**fail-open**，不阻塞请求，
  也不会误删他人持有的锁）。Redis 不可用时与加锁前完全一致地降级读库、不写缓存。
  新增用例 `SysConfigLockTest`（回填写缓存并释放锁、抢不到锁时 fail-open 且不动他人锁）。
- **字典数据缓存（P2-8）**：新增 `support/DictCache.php`，复用 `PermissionCache` 的
  「全局版本号 + 缓存键含版本」范式（`cccms:dict:ver` + `cccms:dict:d:{ver}:{typeId}`，TTL 600）。
  `DictLogic::dataList()` 优先读缓存，字典增删改与**回收站还原 / 彻底删除**均 `bump()` 版本号；
  回收站视图直查库不缓存；Redis 不可用时自动降级直查库，功能不中断。

### 可观测性

- **登录安全分析视图（P2-13）**：登录成功 / 失败早已落在 `sys_log`（`path = '/auth/login'`），
  但**只有明细没有聚合**，撞库 / 异地登录需要人工翻列表。新增
  `GET /log/login/analysis`（权限节点 `cccms:log:analysis`），返回四组聚合：
  失败趋势（窗口 ≤ 48 小时按**小时**分桶，否则按**天**；**补齐空桶**，否则「某天没有登录」
  在图上表现为直接跳过去）、失败 TOP 10 用户名、失败 TOP 10 IP、
  **异地登录**（同一账号两次**成功**登录之间 IP 发生变化）。
  - 汇总用**一条**聚合语句取全（`COUNT(DISTINCT CASE WHEN ... END)` 写在 field 里），
    窗口只扫一遍；同时避开 `distinct()` / `group()` —— 这两个方法只声明在
    `think\db\Query` 上，而 `newScopedQuery()` 声明的返回类型是基类 `BaseQuery`，
    因此对需要分组的两处**显式收窄类型**（`@var \think\db\Query`）而不是改宽共享签名。
  - 数据范围对聚合同样生效（走同一份 `newScopedQuery()`）：「仅本人」档的管理员只统计得到
    自己的登录记录 —— 这也回答了开发计划里「**待确认**：`sys_log` 是否参与数据权限」，
    结论是**参与**。
  - 前端日志页顶部新增「登录分析」标签页（复用 ECharts 折线图；主题 / 语言切换后重绘，
    组件销毁时 `dispose()` 释放实例），**无 `cccms:log:analysis` 权限时不渲染入口**
    （避免「点进去 403」）。首次切到该标签页才发请求，省掉无谓的聚合查询。
  - 新增用例 `LoginAnalysisTest`（4 条，需库）：用**显式时间窗口**把统计范围收窄到用例刚写入的
    记录上（否则结果会被库里既有的真实数据影响而不可断言），覆盖聚合口径、趋势分桶与补空桶、
    以及窗口参数（`days` 上下界、显式区间优先）。
- **日志链路聚合视图（P2-6）**：新增 `GET /log/trace?trace_id=` + 权限节点 `cccms:log:trace`，
  按 `trace_id` 把一次请求的全部日志串起来（按 `id` 升序 = 请求内时间顺序），并汇总
  `{total, failed, cost}`。前端日志页「链路ID」列可点 + 操作列「同链路」按钮 + 详情抽屉内
  「查看同链路」，以 `el-timeline` 时间线展示；支持 **URL 直达** `/log?trace_id=xxx`
  （从报错弹窗跳转即自动展开链路）。走同一份 `newScopedQuery()`，越权日志不出现。
- **可观测端点：`/healthz` 与 `/metrics`（P2-12）**：新增 `app/controller/ObservabilityController`
  与 `support/{HealthProbe,Metrics,EndpointAccess}.php`，两个端点都是 `#[NoLogin]` +
  **IP 白名单**（新增配置 `security.metrics_allow_ips`，默认 `127.0.0.1,::1`），
  非白名单来源返回 **404 而不是 403**（403 等于承认「这个路径存在」）。
  - `GET /healthz` 是**就绪探针**：MySQL / Redis / 磁盘 / 内存逐项检查，正常 200 + JSON 明细，
    任一失败 **503 并指明失败项**。Redis 探活用「写 → 读回 → 删」而不是 PING
    （PING 在只读 / OOM 时仍会通过，而业务依赖的是读写）；容器文件系统拿不到容量信息时
    标记 `unsupported` 而**不误报故障**；`memory_limit = -1` 时只报用量不判故障。
  - `GET /metrics` 输出 Prometheus 文本（`text/plain; version=0.0.4`）：
    `cccms_up{component}`、请求数 / 错误数 / P50·P95·P99 耗时、在线会话数、
    定时任务最近执行状态与时间戳、磁盘与内存。
    **刻意不使用进程内计数器**：Webman 是多进程常驻模型，进程内计数只反映「当前 worker
    处理过多少」，多实例部署下完全失真 —— 因此统一从可共享来源（`sys_log` 滚动窗口 /
    Redis / 库）派生，代价是精度受日志保留策略影响，换来跨进程、跨实例口径一致。
    耗时分位取「窗口内最近 20000 条再排序」而不是 `ORDER BY cost LIMIT`（后者会系统性地
    只取到最便宜的一批）。
  - 探活 / 抓取请求**不写操作日志**（`OperationLog` 的 `SKIP_PATHS`，含 `/ping`）：
    它们是周期性机器请求，写进 `sys_log` 既会淹没业务日志，也会让 `/metrics` 的请求量
    **自反馈虚高**（指标本身就是从 `sys_log` 派生的）。
  - `Dockerfile` 与 `docker-compose.yml` 的 `HEALTHCHECK` 由探 `/ping` 改为探 `/healthz`
    （依赖故障 → 503 → unhealthy）；`/ping` 保留为不碰外部依赖的**存活探针**。
  - 新增用例 `ObservabilityTest`（9 条）：Prometheus 行格式与 `HELP`/`TYPE` 配对、
    标签值转义、数值格式、分位算法、`php.ini` 容量解析、白名单 fail-closed、采集与渲染一致性。

## [1.2.0] - 2026-09-17 · 数据权限下沉到模型层

> 这是本项目规模最大的一次重构：把数据权限从「Logic 层显式调用」改为「模型层自动生效」。

### 新增

- **`BaseModel` 全局查询作用域**：`protected $globalScope = ['dataScope']` +
  `scopeDataScope()` + `$dataScope` 声明位 + `newScopedQuery()`。
- **请求级 scope plan**：`DataScope` 用 `WeakMap`（键为 `UserContext` **实例**）缓存
  角色 / 岗位 / 部门 / 规则 / 受控表，一次请求只解析一次。
  实测：同请求 10 次模型查询 → 数据权限相关 SQL **0 条**（无缓存对照 50 条）。
- **写入侧字段级防护**：`app/model/ScopedQuery.php`（`BaseModel::$query`），
  在 `insert` / `update` / `save` / `insertAll` 前剔除 `hidden` / `readonly` / `mask` / `encrypt` 字段。
- **检查命令 `cccms:data-scope-check`**（`DataScopeChecker`）：
  R1 控制器不得直连数据库；R2 受控表必须有模型且不得声明 `$dataScope = false`；
  自动发现业务插件（以 `db/menu.php` 判定）；首轮即抓出 10 处真实漏网。
- **规则体检 `cccms:data-rule-check`**（`RuleConflict`）：条件互斥 / 同字段多动作 /
  恒不生效 / 表未受控；只报「可证明为空」的组合（宁漏不误）。
- **规则「绑定关系：或 / 且」**：`sys_data_rule.bind_mode`（`or` 默认 / `and`）；
  未填写的维度不参与判断。
- **受控表管理**：`sys_data_scope_table` + 管理界面（哪些表可配**自定义规则**）。

### 变更

- **数据权限语义收紧**：自定义档（`data_scope = 5`）的 fail-closed **无条件成立** ——
  没有规则 / 一条都没命中 = 看不到任何数据。
- **软删除下沉到模型层**：`BaseModel` 使用 think-orm 的 `SoftDelete` trait，
  查询自动排除已删数据；`support/SoftDelete.php` 职责收窄为「查询构造器直查」场景。
- **Logic 层迁移**：用户 / 角色 / 部门 / 岗位 / 附件 / 定时任务 / 操作日志 / 数据权限规则
  共 8 个 Logic 的 `Db::name()` 清零（`information_schema` 反射除外）。
- **`dept` 登记受控表**：可配自定义规则；登记只影响「能否配自定义规则」，
  预设基线由模型声明决定，两者解耦。

### 修复

- **回收站恢复时把待恢复行自己算作占用**：导致 user / role / post / dict_type / menu
  根本无法恢复（查重未排除已删行）。
- **`DashboardLogic` 口径泄漏**：附件 / 日志列表已按数据范围收窄，工作台却仍显示全量总数；
  现全部改为模型查询，随范围聚合（超管 `user=2 dept=2 log=33` → 仅本人档 `user=1 dept=0 log=0`）。
- **`dept` 登记后被检查命令抓出的漏网**：`ProfileLogic` 仍在用 `Db::name('dept')`，已迁移。
- **数据规则「排序」字段是个假旋钮**：运行时完全不读 `sort`，但字段级动作是**按顺序依次处理**的，
  原先不指定顺序导致结果不可复现；现固定 `ORDER BY id ASC`，并移除该字段。

### 移除

- Logic 层的 `DataScope::field()` / `stripRow()` / `stripProtected()` 调用与旧方法（改由模型层承担）。
- `sys_data_rule.sort` 列（不影响规则生效，界面上也不展示）。

## 附录 A · 数据权限迁移决策与验证记录

> 以下为 `[1.2.0]` 迁移过程中的决策与实测数据，保留作为设计依据（由原 `待办.md` 整理）。

### A.1 三个必须区分开的概念

| 概念 | 含义 | 决定方 |
|---|---|---|
| **模型化** | 该表查询改走 `Model` 而不是 `Db::name()` | 各模块迁移进度 |
| **参与数据权限** | 是否走预设基线（仅本人 / 本部门） | 模型的 `$dataScope` 声明 |
| **登记受控** | 是否可配**自定义**行级 / 字段级规则 | `sys_data_scope_table` |

### A.2 三条设计铁律

1. **表名以模型为准**：`applyToModelQuery()` 强制用 `$model->getName()` 覆盖声明里的表名。
2. **用户上下文只从 `request()->user` 取**，不新建静态容器（非 fiber 环境下
   `Workerman\Coroutine\Context\Fiber` 会把数据写进 worker 级全局，导致跨请求身份泄漏）。
3. **无用户 ⇒ 不作用域**（fail-open，但边界封闭）：只剩登录链路、CLI、`#[NoLogin]` 三类场景，
   且 `CheckLogin` / `CheckAuth` 会先对受保护路由抛 401。

### A.3 表 → 语义 → 状态

| 功能模块 | 表 | 模型 | owner（仅本人） | dept（本部门） | 模型声明 | 登记受控 |
|---|---|---|---|---|---|---|
| 用户管理 | `sys_user` | `User` | `id` | 经 `sys_user_dept` | 参与 | 已登记 |
| 部门管理 | `sys_dept` | `Dept` | 我所属部门 | 部门子树（`id IN`） | 参与 | 已登记 |
| 附件管理 | `sys_file` | `File` | `create_by` | 经 `create_by` → `sys_user_dept` | 参与 | 已登记 |
| 定时任务 | `sys_crontab` | `Crontab` | — | — | 参与（`no_baseline`） | 已登记 |
| 操作日志 | `sys_log` | `OperationLog` | `user_id` | 可见部门成员 | 参与 | 已登记 |
| 角色管理 | `sys_role` | `Role` | — | — | 不参与（已定） | 不登记（已定） |
| 岗位管理 | `sys_post` | `Post` | — | — | 不参与 | 不登记 |
| 数据权限规则 | `sys_data_rule` | `DataRule` | — | — | 不参与（已定） | 不登记（已定） |
| 通知公告 | `sys_notice` | `Notice` | — | — | 不参与（广播内容无归属） | 不登记 |

**明确不纳入范围**：`sys_menu` / `sys_role_node`（权限节点树，与数据权限正交）、
`sys_config`、`sys_dict_*`、`sys_category`、`sys_data_scope_table`、
`sys_crontab_log`、全部关联表（`sys_user_role` / `sys_user_dept` / `sys_user_post` / `sys_dept_role`）。

### A.4 绑定语义实测（`or` / `and`）

规则统一把 `user` 表收窄成 `id = 1`，命中即可见 1 行：

| 场景 | `or` | `and` |
|---|---|---|
| 无规则 | 0 | 0 |
| 只绑「自己有的岗位 A」 | 1 | 1（未填项不参与） |
| 「别人」+「自己的岗位 A」 | **1** | **0** |
| 「自己」+「自己的岗位 A」 | — | 1 |
| 「自己」+岗位 A + 部门 #1（三项） | — | 1 |
| 四项全绑、角色绑错 | — | **0** |
| 四项都不填（全局） | 1 | 1 |
| `bind_mode = 'AND'`（大写） | — | 按 `and` 生效 |
| `bind_mode = 'xxx'`（非法） | — | 兜底按 `or` |

### A.5 端到端验证矩阵（`[1.2.0]`）

| 场景 | 结果 |
|---|---|
| 超管 | `SELECT * FROM sys_user`（无范围条件）✓ |
| 仅本人 | `User` → `WHERE id = '990099'`；`File` → `WHERE create_by`；`Dept` → 我所属部门 ✓ |
| 仅本人 | `Role` / `Menu` → 无任何条件（声明不参与）✓ |
| 本部门及以下 | `Dept` → `WHERE id IN ('1','2')`（子树展开）✓ |
| 全部数据 / 无用户 | 无范围条件 ✓ |
| 逃生口 | `User::withoutGlobalScope()` → 无条件 ✓ |
| 越权拦截 | `read` / `update` / `delete` / `resetPassword` 对他人 id 全部 403 ✓ |
| 唯一性校验 | 仍能看全量（重名被正确拒绝）✓ |
| 请求级缓存 | 同请求 10 次模型查询 → 权限 SQL 0 条；无缓存对照 50 条 ✓ |
| 部门树作用域过滤 | 可见节点父不在集合时**提升为顶层**，否则整树为空 ✓ |
| 字段级规则 | 出参 `phone = 138****0000`；`update` 提交掩码 / 只读字段**均未写入** ✓ |
| 软删除 | 列表排除 / 回收站包含；未加 `withTrashed()` 的更新实测 0 行（陷阱确认）✓ |

### A.6 关于 `ks_*` 表（已定案）

`sys_data_scope_table` 里的 6 张 `ks_*` 表（`ks_subject` / `ks_account` / `ks_asset` /
`ks_rule` / `ks_alert` / `ks_batch_job`）属于**下游业务插件系统**。
本仓库是基础系统、不负责它们的 Logic；检查命令对「主代码中找不到模型的受控表」
只报 `NOTICE`，不计入错误，CI 不会被它们卡住。
